# 项目展示与后续补强

[返回文档索引](README.md)

项目定位：基于 GD32E505 / FreeRTOS 的数据采集与通信平台。
展示重点是数据管理、通信组织、内存与同步取舍、工具链和验证证据。
当前业务点表仍为 IDU/FAN 各 50 个 TEST 测点；实际风扇控制业务尚待接入。

## 已有亮点与代码入口

| --- | --- | --- |

第三方基础包括 FreeRTOS、nanoMODBUS、SFUD、FlashDB、nr_micro_shell 和
EasyLogger。介绍时分别说明上游能力，以及自己的适配、映射、调度和验证工作。

2026-10-15 本地补强验证：主机 34/34 组、配置矩阵 6/6 组，以及
Debug / Release / product 三种固件构建通过。主机新增基准故障注入与比较条件
检查；数据库验证零版本兼容、业务版本变化及初始化写入失败恢复。
这些是本地软件验证记录，本轮未进行实板验收或远端 CI 执行。

## 可演示的五条链路

### 1. 增加或调整测点

在独立工作分支修改 `app/protocol/config/points.json`，调整 TEST 测点默认值、
访问权限或新增测点，再执行：

```sh
source .venv/bin/activate
python scripts/generate_points.py --validate
python scripts/generate_points.py
python scripts/generate_points.py --check
python tests/points/run.py
python scripts/build.py
```

展示输入到枚举、C 定义、Modbus 映射、容量和持久化清单的关联。
再故意配置重复 Key 或重叠从站地址，展示生成阶段拒绝错误，修正后再构建。
生成器负责检查和渲染；板级端口、回调实现及任务资源仍由应用配置。

### 2. 类型、范围和持久化

在测试板控制台执行以下命令，使用不会被测试任务每秒修改的 IDU TEST_003：

```text
sig get 1 2003
sig set 1 2003 12345
sig get 1 2003
sig save 1 2003
sig set 1 2003 23456
sig load 1 2003
sig get 1 2003
```

最后应读回 12345。随后手动复位，再检查启动恢复。
空白数据库需要先在测试分区执行 `db init`；该命令允许修复或格式化无效介质。
保存命令会写入实际 Flash，演示前使用专用测试数据。

版本演示：将该持久化项 `data_version` 从 0 改为 1，重新生成、构建和烧录。
新固件打开数据库时作废该项旧快照，aBus 保留默认值；其他兼容项保持原值。
保持版本再复位，不应重复作废或写入兼容性标记。
版本相等才兼容，回退版本同样可能作废记录；当前策略不迁移旧值。

主机可先演示 `python tests/database/run.py`，其中真实 FlashDB 配合 NOR 模型
检查版本变化、零版本兼容、GC 和逐次写入失败。它不能代替真实掉电验证。

### 3. 采集计划与临时请求

```sh
python scripts/benchmark.py --output build/benchmarks/showcase
```

当前 FAN 表有 50 条映射、30 项参与轮询。计划基准对比原配置和逐点断帧配置：
原配置为 6 帧，逐点断帧为 30 帧，帧数减少 80%。这是无 I/O 的计划构建结果，
不能据此宣称采集耗时减少 80%；真实线路还受波特率、响应时间和重试影响。

上板准备匹配点表的从站或模拟器，观察 `protocol stats`，并用串口抓包确认
周期读取、临时写入及断线恢复。主从站和测试下发配置见
[产品协议](../app/protocol/README.md)，演示前记录配置，避免把重试算成成功采集。

### 4. 性能测量及资源使用

```text
sys heap
bench bus
sys heap
sys stack shell
sys stack modbus
protocol stats
```

先空闲测量，再在轮询、日志、数据库负载下测量。任务名以当前构建为准。
保存固件 SHA256、构建摘要、CPU 频率、锁模式、负载、原始输出和栈余量。

主机报告是纳秒，板端入口是 CPU cycles；两者不可直接相互替代。
当前分位数描述每批平均耗时，不代表单次调用的尾延迟。
新版基准在计时外验证写入效果；工作负载版本不同的报告不自动计算比值。
详细范围与复测命令见[性能基准](../benchmarks/README.md)。

### 5. 可重复验证和故障定位

```sh
python scripts/test.py --suite host
python scripts/test.py --suite firmware
python scripts/test.py --suite matrix
```

展示测试失败日志、配置矩阵和构建摘要。CI 配置保留各 suite 的报告与固件产物，
产物名包含提交 SHA；远端是否实际执行和上传，以 Actions 记录为准。
现场异常可结合故障快照与对应版本 ELF/MAP 定位。异常入口及复位保留 SRAM 的
完整硬件验证仍待完成，不能仅凭主机快照测试宣称已通过。

## TTL 单端口采集与转发：后续设计，尚未实现

目标是同一物理 UART 承担采集事务和转发业务。TTL UART 的收发线独立，
可以同时收发；具体报文仍需能够区分响应和转发，不能由电气全双工推导出协议可混用。
RS485 也能分时承担两种业务，但还需安排总线占用、方向和主站仲裁。

推荐边界：

```text
物理串口 RX → 唯一接收入口 → 协议解析/报文归属回调
                              ├→ 采集事务响应
                              └→ 转发处理

采集请求 / 转发报文 → 统一发送队列 → 按完整帧提交串口 TX
```

- aDrv/aDevice 提供字节收发及硬件状态；不识别业务命令。
- aComm 管理通道占用、发送排队、预算和通知，通过注册回调识别报文归属；
  它不写死 Modbus 或其他协议的报文格式。
- 协议模块负责分帧、校验和提取命令字、地址、事务号等识别信息。
- 应用配置端口、协议实例、采集点表、转发路由和任务资源。

接收只能有一个消费者，不能让采集和转发任务分别读取同一字节流。
发送队列必须防止两个报文交错；排队超时与发出后等待响应的超时分别定义。
优先级与配额需要防止持续转发挤占采集，并规定满队列时拒绝、丢弃还是背压。
数据借用到何时、关闭时如何处理在途事务、迟到响应如何丢弃也要明确。

当前同步 Modbus 事务会读取自己的端口，不能直接用两个实例共享同一读入口。
后续接入统一接收分发时，需要为事务提供已路由的响应数据，并检查协议本身是否
能区分并发请求；普通 RTU 无事务号，单凭 TTL 接口仍不能任意并发事务。
透明字节转发与本地采集混用时也可能没有可判定边界，必须先约定帧格式或独占时段。

实现前先确定两点：转发对象和方向；线上协议如何区分采集响应与待转发报文。
本轮只记录目标，不增加新的模块、线程或端口配置。

## 简历表述和面试追问

可根据自己实际承担的工作选用：

- 设计 GD32 / FreeRTOS 数据采集通信平台，实现多设备数据总线、静态内存绑定、
  动态存储补充分配及参数持久化。
- 基于 nanoMODBUS 实现通信映射和通用调度，支持周期采集、临时请求、地址合并
  和断帧配置；演示点表中将 30 个轮询项合并为 6 个请求。
- 建立 JSON Schema、Python、Mako 点表生成和自动回归链路，统一数据定义、
  协议映射与持久化清单，校验地址冲突、类型长度及结构体布局。

面试可重点解释：

1. 为什么 Index 与 Key 分开，升级重排如何保持存储标识稳定。
2. 为什么静态定义放 Flash，少量绑定如何与动态托管数据共存。
3. 首成员与回调如何解耦，哪些约束由编译期、初始化和运行期分别检查。
4. 为什么写请求不能默认无限重试，超时是否代表远端没有执行。
5. 为什么 DMA 完成与线路发送完成不同，RS485 DE 在何时释放。
6. 为什么布局相同不等于业务兼容，版本变化和掉电顺序如何处理。
7. 性能基准如何证明真实完成了读写，计时区间和统计口径如何确定。

介绍范围应准确：当前是 GD32 / FreeRTOS 实现，Linux 后端和 QSPI 后端仍待完成；
静态实例可能创建 OS 堆对象；默认应用串口路径为 IRQ 缓冲，DMA/Async 能力须按
实际配置和硬件验证说明。product 配置隔离主动测试任务，仍保留 TEST 点表，
尚未完成真实产品验收。自有代码许可证由维护者确定。
